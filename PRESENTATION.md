## 1. The Problem

From the PRD (`PRD.md` §2):

1. **Payment instruments assume a human.** Developers who want a card for tests,
   subscriptions, or automation must use dashboards built for manual use. Adding a
   card to a script or CI job is awkward or impossible.
2. **AI agents can't parse fintech UIs.** Agents are increasingly expected to complete
   purchases, but most card products return prose or HTML instead of structured data.
3. **On-chain balances can't easily become spendable cards** without leaving the
   developer workflow.

> **The gap:** there is no small, scriptable path from *"fund an address"* to
> *"hold a virtual card"* that an agent can drive end to end.

---

## 2. The Solution

**StellarCard = CLI + Soroban contract + web demo.** Three independent surfaces, one
flow:

```
deposit address (Stellar keypair)
        │  XLM / USDC on testnet
        ▼
Horizon observation ──► local USD balance (live Coinbase XLM-USD price)
        │
        ▼
card buy ──► Soroban fee vault `collect_fee` (fee in XLM, payer = tx source)
        └──► Stripe Issuing test mode virtual card
```

What each piece does:

- **Deposits** — per-deposit Stellar accounts generated by the CLI. Balances and
  funding transactions are read from Horizon. USDC uses the Circle testnet issuer and
  requires a trustline (`deposit trustline`).
- **Fees** — fixed **$0.10 + 0.20%** per card, converted to XLM at the live Coinbase
  spot price and paid on-chain through the Soroban fee vault.
- **Cards** — Stripe Issuing **test mode** (cardholder + virtual card). The CLI returns
  what Stripe exposes and stores nothing beyond the summary.
- **Web demo** — same flow from the browser: Freighter pays the fee on-chain, a
  Cloudflare Pages Function verifies the tx on Horizon, then issues the Stripe
  test-mode card.
- **State** — local JSON/TOML under `~/.config/stellar-card`, `0600` permissions, no
  database, no server.

## 4. How It Works — End-to-End Flow (presenter narrative)

1. **Auth** — developer/agent stores a Stripe **test** key (`auth login`). The CLI
   validates it against Stripe and stores it in `credentials.toml` (`0600`).
2. **Deposit address** — `deposit address --asset xlm` generates a fresh ed25519
   keypair, derives the `G...` address, and persists a deposit record locally.
3. **Fund** — `deposit fund <id>` calls Friendbot (testnet) and returns the funding
   transaction hash.
4. **Observe** — `deposit status <id> --wait` polls Horizon, reads the native balance
   (or the USDC balance for the exact issuer), prices it with the live Coinbase
   `XLM-USD/spot` endpoint, and credits a local USD balance. Exit code `10` means
   pending; `confirmed` credits the balance.
5. **USDC path** — `deposit trustline <id>` builds, signs, and submits a classic
   `ChangeTrust` operation for USDC.
6. **Buy** — `card buy --amount 5.00`:
   - validates the $5.00–$500.00 range and local balance (amount + fee),
   - quotes the fee **$0.10 + 0.20%** in XLM at the live price,
   - picks a fee payer (configured wallet or a confirmed XLM deposit with reserve),
   - simulates, assembles, signs and submits `collect_fee(payer, amount, fee_reference)`
     to the Soroban vault, then polls until the ledger confirms,
   - creates a Stripe cardholder (once) and a virtual card,
   - returns the card summary + `fee_payment.transaction_hash` and `fee_stroops`.
7. **Reveal** — `card show <id>` retrieves the card from Stripe; if Stripe exposes
   PAN/CVC they are returned once, otherwise a `reveal_unavailable_reason`.
8. **Freeze** — `card freeze <id> --confirm` sets the card to frozen; `--dry-run`
   previews without calling Stripe.
9. **(Optional) On-ramp** — `onramp start` opens a SEP-24 interactive deposit at an
   anchor; when the anchor completes, the linked deposit is credited.

## 5. Architecture & Tech Stack

### System diagram

```
CLI (Rust)                        local disk
  auth / deposit / card /         config.toml, credentials.toml, state.json
  onramp / balance / config  ───► (0600, no DB, no server)
        │
        ├── Stripe API (Issuing, test mode) .... cardholder + virtual card
        ├── Horizon (testnet) .................. account state, payments,
        │                                        balances, Friendbot, tx submit
        ├── Coinbase spot API .................. XLM/USD price for fee quotes
        └── Soroban RPC (testnet) .............. collect_fee (only when enabled)

Web demo (Next.js static export on Cloudflare Pages)
  Browser (Freighter) ── sign collect_fee tx ──► Soroban testnet
  Cloudflare Pages Function ── verify on Horizon ──► Stripe Issuing (test)
                            └── card↔cardholder mapping in Cloudflare KV
```

### Stack table

| Layer | Technology |
|---|---|
| CLI | Rust 1.97.1 (pinned by `rust-toolchain.toml`), clap 4, tokio, reqwest (rustls) |
| Stellar | `stellar-xdr` 28, `stellar-strkey`, ed25519-dalek, hand-built classic txs, Soroban RPC simulate/assemble/sign/send |
| Contract | `soroban-sdk` 28, wasm32v1-none target, `stellar contract build` |
| Payments | Stripe Issuing (test mode) via REST |
| Price feed | Coinbase `v2/prices/XLM-USD/spot` |
| Web | Next.js 16 (static export `output: "export"`), React 19, Tailwind 4, framer-motion, `@stellar/freighter-api`, `@stellar/stellar-sdk`, qrcode.react |
| Edge | Cloudflare Pages Functions + Cloudflare KV |
| Tests | `cargo test`, wiremock HTTP mocks, assert_cmd/predicates, soroban testutils |

### Why these choices (talking points)

- **Rust for the CLI** — a single static binary, no runtime, deterministic behavior,
  exact integer money math, overflow checks enabled in release.
- **Hand-rolled Stellar tx assembly** (`src/tx.rs`, `src/soroban.rs`) — no SDK black
  box; signing, XDR, and Soroban auth entries are explicit and unit-tested.
- **Static export + edge functions for web** — no server to operate; Stripe secrets
  live only as Cloudflare Pages secrets, never in the browser.
- **Local state only** — no database, no hosted API, nothing to breach; the CLI is the
  product.

### 7.2 The agent contract

- **Success** — one JSON object on stdout:
  `{"ok": true, "data": {...}, "meta": {"request_id": "req_...", "timestamp": "..."}}`
- **Failure** — JSON on stderr:
  `{"ok": false, "error": {"code", "message", "details", "suggestion"}, "meta": {...}}`
- **Stable exit codes:**

| Exit | Code | Meaning |
|---|---|---|
| 1 | `GENERAL_ERROR` | General |
| 2 | `INVALID_ARGUMENTS` | Usage |
| 3 | `AUTHENTICATION_FAILURE` | Auth |
| 4 | `INSUFFICIENT_BALANCE` | Insufficient balance |
| 5 | `RESOURCE_NOT_FOUND` | Not found |
| 6 | `RATE_LIMITED` | Rate limited |
| 7 | `EXTERNAL_SERVICE_ERROR` | External service |
| 8 | `NETWORK_ERROR` | Network |
| 10 | `DEPOSIT_PENDING` | Deposit still pending |

- **Idempotency:** retrying `deposit address` or `card buy` with the same
  `--idempotency-key` returns the previously created resource instead of a duplicate.
- **No prompts, ever** — destructive actions require an explicit `--confirm`.
- Error payloads carry a **`suggestion`** field so an agent can self-correct
  (e.g. "Deposit at least $X more. Run: stellar-card deposit address").

## 8. Fee Model

- **Formula:** `fixed $0.10 + 0.20% (20 bps)`, rounded **up** at the cent.
- **Settlement asset:** XLM (stroops; 1 XLM = 10,000,000 stroops).
- **Conversion:** live Coinbase `XLM-USD/spot`; falls back to configured
  `xlm_price_usd` when unreachable. Rounds up, never zero.
- **Example ($5.00 card):** fee = $0.10 + $0.01 = **$0.11**. At the observed
  testnet-time price this was **5,789,474 stroops** (~0.579 XLM) — the exact amount
  that landed in the vault, twice.
- **On-chain collection is opt-in** (`onchain_fee_collection_enabled`, default
  `false`). When enabled, `fee_contract_id` is required and `collect_fee` is invoked.
- **Money math:** integer stroops/cents everywhere; overflow checks enabled in
  release builds (`overflow-checks = true`).

> Screenshot-worthy line: *the fee is visible in the JSON, in the Stellar
> transaction, and in the vault's on-chain state — there is nowhere to hide a spread.*

### Invariants and defense (great slide material)

- `withdraw` can never exceed `total_collected - total_withdrawn`.
- All totals use `checked_add` / `checked_sub`; overflow maps to `MathOverflow`.
- Accounting is updated **before** the token transfer; Soroban forbids re-entering the
  same contract, so accounting cannot be corrupted re-entrantly.
- `collect_fee` and `update_pricing`/`withdraw` use `require_auth`; the native token
  address is fixed at `initialize` and cannot be changed.
- Deliberately minimal: one authority, no upgrade path, no pause, no other admin
  functions. TTL extended to 30 days on every mutation.
- 7 explicit error variants (`AlreadyInitialized`, `NotInitialized`, `InvalidFeeBps`,
  `InvalidAmount`, `MathOverflow`, `InsufficientVault`, `Unauthorized`).
- Typed events (`initialized`, `fee_collected`, `withdrawn`, `pricing_updated`)
  decodable from the contract spec.
- **13 contract tests** cover initialization, auth failures, collection accumulation,
  withdrawal limits, pricing validation, and error paths.

## 10. Stellar Integration Details

### Deposits (Horizon)

- Each deposit is a **fresh keypair**; the address and secret are stored in local
  state (`0600`).
- `observe_deposit` reads the account from Horizon:
  - **XLM** — native balance × live Coinbase price, integer math, exact 7-decimal
    parsing.
  - **USDC** — sums only balance lines matching both asset code `USDC` **and** the
    configured issuer (Circle testnet issuer
    `GBBD47IF6LWK7P7MDEVSCWR7DPUWV3NY3DTQEVFL4NAT4AQH3ZLLFLA5`).
- **USDC trustline** — classic `ChangeTrust` (credit_alphanum4) built by hand,
  signed with ed25519, submitted as base64 XDR to Horizon. Live-verified.
- **Friendbot** — funding helper for testnet; the CLI records the funding tx hash.

### Soroban invocation path (`src/soroban.rs`)

`simulateTransaction` → assemble footprint/auth/resources → sign with the payer →
`sendTransaction` → poll `getTransaction` (60 attempts, 500 ms interval, retries on
`tryAgainLater` / `NOT_FOUND`). The payer is both the `payer` argument and the
transaction source, so Horizon authorization and contract `require_auth` agree.

### USDC issuer

Testnet USDC issuer: `GBBD47IF6LWK7P7MDEVSCWR7DPUWV3NY3DTQEVFL4NAT4AQH3ZLLFLA5`.
Recipients need a trustline before the account can receive USDC; XLM needs none.

## 11. Fiat On-Ramp (SEP-1 / SEP-10 / SEP-24)

The CLI ships an **anchor-agnostic** on-ramp client (`src/anchor.rs`):

- **SEP-1** — reads `/.well-known/stellar.toml` for endpoints and supported currencies.
- **SEP-10** — signs the anchor's challenge transaction with the deposit key and
  exchanges it for a JWT (`sign_envelope`, real ed25519 signatures; rejects network
  passphrase mismatches).
- **SEP-24** — opens an interactive deposit at the anchor and polls its status;
  completion credits the linked stellar-card deposit.

```bash
stellar-card onramp info
stellar-card onramp start --asset usdc --amount 10   # → interactive_url
stellar-card onramp status ramp_...                  # pending → completed
stellar-card deposit status <dep-id>                 # credited once funds arrive
stellar-card card buy --amount 5.00                  # spend it
```

## 12. Web Demo & Edge Issuance

**Live:** <https://card.batuhan4.com> (fallback <https://stellar-card-54s.pages.dev>).
Next.js **static export** on Cloudflare Pages with edge functions — no server to run.

**This is not a mock. Every step touches real infrastructure:**

1. Freighter signs a real Soroban `collect_fee` transaction on Stellar testnet.
2. A Cloudflare Pages Function (`web/functions/`) verifies it on Horizon:
   - transaction **succeeded**,
   - **fresh** (< 20 minutes),
   - contains a **native transfer to the fee vault** **from the payer**,
   - amount covers the quoted **$0.10 + 0.20%** fee (5% price-drift tolerance).
3. The same function issues a real Stripe **test-mode** virtual card and stores a
   card↔cardholder mapping in Cloudflare KV.
4. Freeze calls Stripe directly from the edge function.

**Edge API surface:**

| Method | Route | Purpose |
|---|---|---|
| `POST` | `/api/card` | Verify on-chain fee → issue card |
| `GET` | `/api/card/:id` | Read card, PAN/CVC only for the cardholder email |
| `POST` | `/api/card/:id/freeze` | Freeze card |
| `GET` | `/api/cards?email=` | List cards for an email |

**Edge security properties:**

- A fee transaction can be used **once** — replays return **HTTP 409**.
- PAN/CVC are returned only for the cardholder's email; other reads return **403**.
- `livemode: false` is exposed in every response.
- `STRIPE_TEST_KEY` is a Pages secret and never reaches the browser; the only public
  config is `NEXT_PUBLIC_FEE_VAULT_CONTRACT_ID`.
- KV namespace `STELLAR_CARD_KV` = `55926b9b6752448ea08f05d30bf44253`.

**Pages:** `/` (landing, pricing, overview), `/dashboard` (balance, cards, deposits),
`/deposit` (address + QR, Friendbot, Horizon monitoring), `/cards` (fee payment with
Freighter, card reveal, freeze).

## 15. Security, Compliance, Boundaries

- **Testnet only.** Direct mode refuses `mainnet` (`ensure_testnet`). Stripe Issuing
  test mode issues non-spendable cards. There are no real funds anywhere.
- **Secrets stay local.** Stripe test key and Stellar secret keys live in
  `~/.config/stellar-card` (`0600`), are masked in output, and are never committed.
- **PAN/CVC are sensitive.** Reveal returns them once, stores only what Stripe
  returns; the skill instructs agents never to log or forward them.
- **Authorization before spend.** `card freeze` requires `--confirm`; on-chain fee
  collection requires explicit opt-in; the vault checks auth on every mutating call.
- **Integer money math** (stroops, cents); overflow checks on in release builds.
- **Not a regulated business.** Not a bank, custodian, exchange, anchor, or KYC
  provider. No yield or investment claims; fees are product pricing.
- **No fabricated evidence policy.** No hash/id/address is written down before it is
  observed on-chain; the agent skill repeats this as a hard rule.

## 17. Limitations, Non-Goals, Future Work

**Honest limits (say these before judges ask):**

- Card value: **$5.00 – $500.00**.
- Direct mode is testnet-only; mainnet requires validation and a live Stripe key.
- Stripe test-mode cards are **not real cards** and cannot be spent.
- Stellar testnet resets periodically; the vault must be redeployed after a reset.
- No TRY anchor exists yet — integration is ready, counterparty is missing.
- Balances are local: confirmed deposit credits minus card debits. No ledger
  reconciliation service.

**Explicit non-goals:** mainnet issuance, fiat custody/exchange/KYC, multi-chain,
hosted API, teams/multi-tenancy, webhooks, programmable spend policies.

**Natural next steps:**

1. Mainnet configuration path with live Stripe key and compliance review.
2. Publish the npm wrapper (`stellar-card`).
3. Spend policies / card-level limits for agents.
4. TRY on-ramp the moment a licensed SEP-24 anchor exists.

## 20. Q&A Cheat Sheet

**"Is this a real card?"**
No — Stellar testnet and Stripe Issuing test mode. The integration is real; the value
is not. That boundary is deliberate and disclosed everywhere.

**"Why Stripe and not native Stellar card issuance?"**
Stellar has no native card issuance; Stripe is the issuer rail. The novel/verified
part is the Stellar side: deposits, trustlines, Soroban fee settlement, and on-chain
verification before issuance.

**"What stops someone from reusing a fee transaction on the web demo?"**
Cloudflare KV replay guard: the tx hash is claimed before issuance and marked issued
after; replays get HTTP 409. Fee txs are also freshness-bounded to 20 minutes and
must be a native transfer from the payer to the vault covering the quoted fee.

**"Can an agent abuse the CLI?"**
It is testnet-only by construction; `mainnet` is refused; freeze needs `--confirm`;
fee collection is opt-in; secrets are local and masked.

**"Why a Soroban contract at all — why not send XLM directly?"**
The vault gives on-chain, auditable fee accounting (`total_collected`,
`payment_count`, events), authority-only withdrawal, and typed errors. It also proves
the team can ship a real Soroban contract, not just call one.

**"What about fees/UX for the user?"**
Fixed $0.10 + 0.20%, quoted transparently in the JSON before payment, settled in XLM
at the live spot price. No hidden spread.

**"What's the business model?"**
Per-card fee; the same fee rail could meter any agent action (subscriptions, API
calls). Today it funds the card flow.

**"What was hardest?"**
Hand-building and testing Stellar transactions and Soroban auth/assembly without an
SDK, and verifying fee amounts on-chain at the edge with integer math and drift
tolerance.

**"What did AI do?"**
See §16. AI assisted development; all on-chain artifacts are real and verifiable, and
the disclosures are explicit.

## 21. Glossary

| Term | Meaning |
|---|---|
| **Horizon** | Stellar's HTTP API for accounts, balances, transactions |
| **Soroban** | Stellar's smart-contract platform |

| **SEP-1** | `stellar.toml` discovery of anchor endpoints/currencies |
| **SEP-10** | Stellar Web Authentication (signed challenge → JWT) |
| **SEP-24** | Hosted/interactive deposit & withdrawal (anchor KYC flow) |
| **Freighter** | Stellar browser wallet extension |
| **Cloudflare Pages Function** | Edge serverless function (verifies fee, issues card) |
| **Idempotency key** | Client-provided key making a create retry-safe |
| **Test mode** | Stripe environment that issues non-spendable cards |
